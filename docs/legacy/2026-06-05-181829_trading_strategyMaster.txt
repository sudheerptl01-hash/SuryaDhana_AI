⏺ Good question — this is an important distinction. Let me make it concrete.

  What prob_up is supposed to be

  The RL agent (the PPO portfolio optimizer) learns to allocate capital across 
  stocks based on the ML model's signals. Each training "signal" for a stock on
  a given day carries a prob_up — which is meant to be the XGBoost classifier's 
  predicted probability that that stock rises. That's the number the RL agent is
  supposed to react to.

  What I actually feed it (the proxy)

  In the historical RL training path, for each (stock, date) row I compute:

  prob_up = clamp(rsi_14 / 100)      # e.g. RSI 70 → prob_up 0.70

  That's a deterministic formula derived from one real feature (RSI) — not the
  model's output. It's a real, sensible-ish number (and a huge step up from the
  old code, which used np.random — pure noise). But RSI=70 → 0.70 is just a
  heuristic; it is not what your trained XGBoost would actually predict for that
  row.

  Why I used the proxy

  The model's real scoring (/batch-predict) only scores the latest row per
  ticker — today's features. To get the real prob_up for every (stock, date)
  across history (~175k rows), I'd have to run the XGBoost model over all those
  historical feature rows. There's no endpoint that does that historical batch
  scoring, so I substituted the RSI proxy.

  Why it matters — train/serve skew

  - At training time (historical RL), prob_up = RSI proxy.
  - At live inference (the autopilot's intraday loop), prob_up = the real model
  output from /batch-predict.

  So the RL agent learns a policy reacting to one kind of signal, then gets fed
  a different kind of signal in production. The agent's behavior may not
  transfer well. (Note: the latest-day loader in rl_trainer.py does use the real
  batch-predict scores — it's only the historical training batches that use the
  proxy.)

  The proper fix

  Generate real historical model scores and feed those to RL. Two clean ways:
  1. ml-service /score-historical — pull historical features from the DB, run
  them through the active model, return real prob_up per (stock, date).
  2. Persist predictions — write model scores to an ml_predictions table
  whenever the model runs, and have RL read from there (then it's the same
  single-source story).

  Either makes RL train on the same signal it'll see live — closing the skew.

  Want me to implement #1 (historical scoring) so RL trains on real model
  probabilities? It's a focused add: one ml-service endpoint + swapping the
  proxy line in /rl-train to call it.

  Two filter mechanics:
  - Numeric filters (FIELD_MAP) — you pick the operator (<, >, ≤, ≥) and a
  threshold. Evaluated per-row against the computed indicator column.
  - Boolean toggle filters (BOOLEAN_FILTERS) — on/off vectorized predicates, no
  threshold (e.g. golden cross, price-above-MA).

  The critical bias distinction

  This is the part that matters most for trustworthy results:

  ✅ Technical filters are point-in-time / trailing — zero look-ahead. Every
  indicator in compute_indicators() (MA50, MA200, RSI, ATR, 52w hi/lo, vol20) is
  a strictly backward-looking rolling window, so on any historical date they
  only see data up to that date.

  ⚠️ Fundamental filters (P/E, Dividend Yield, Market Cap, ROCE) carry 
  look-ahead bias. They come from a single current snapshot (stock_metrics), not
  a point-in-time history. So if you filter "P/E < 25" on a date in 2023, the
  engine applies today's P/E to that 2023 date. The code flags these explicitly:
  - Tagged in FUNDAMENTAL_FIELDS (backtest_engine.py:28)
  - fundamental_filters_active() detects them
  - The UI shows a ⚠ next to each one and a red warning banner when any is
  active (BacktestPanel.tsx:375)

  Beyond filters — the other "things you control"

  Filters are only the selection layer. The backtest also applies these
  gates/physics, which aren't filters but shape which trades survive:

  - Scope — Full Universe vs. your Watchlist
  - Window — date range (6M/1Y/2Y/3Y/5Y presets)
  - Entry timing — next_open (no same-bar look-ahead) vs. close
  - Risk exits — stop-loss (-2% default), trailing stop, time-stop (5 days)
  - Capital constraints — max 5 concurrent positions, friction (15 bps
  round-trip), DD circuit breaker
  - Win threshold — net % a trade must clear to count as a win
