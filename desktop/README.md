# SuryaDhana.app — the desktop shell (Tauri v2)

A ~10 MB native macOS app (system WKWebView, no bundled browser) that is the window and menu-bar control
panel for the local SuryaDhana stack. **The stack is unchanged and keeps running without the app**:
data-service :8001, ui-api :8010 and master-controller :8008 stay launchd-supervised services
(`com.suryadhana.watchdog`), so the 18:30 EOD pipeline, the Desk, the shadow, backups and Telegram never
depend on a window being open. PAPER ONLY: the shell has no trading code path.

```
macOS login ─► launchd
   ├─ com.suryadhana.watchdog / com.suryadhana.awake           (the stack; untouched by the app)
   └─ ~/Library/LaunchAgents/SuryaDhana.plist  (Launch at Login + relaunch after a crash, written by the app)
          SuryaDhana.app
          ├─ Rust core: health poller · tray · native menu · notifications · downloads · windows · logs
          ├─ boot page    tauri://localhost/index.html      (bundled; capability "boot-local")
          └─ terminal     http://127.0.0.1:8010/?tab=<id>   (remote; capability "terminal-remote")
```

## Build, install, test

```bash
scripts/build_desktop.sh                      # build + ad-hoc sign + verify + size report + build id
scripts/build_desktop.sh --install            # … and install to /Applications (or ~/Applications), keeping the old copy
scripts/build_desktop.sh --install --relaunch # … and start it (through launchd when Launch at Login is on)
scripts/build_desktop.sh --rollback           # swap back to the kept previous copy (again = roll forward)
scripts/build_desktop.sh --install --test     # self-test the BUILT app first; install only if it passed (R1)
scripts/build_desktop.sh --no-build --test    # self-test the existing build
/Applications/SuryaDhana.app/Contents/MacOS/SuryaDhana --version   # "SuryaDhana 1.0.0 (<build id>)", no window
SURYADHANA_UI_URL=http://127.0.0.1:8098 scripts/build_desktop.sh --no-build --test   # against a scratch UI server

cd desktop/src-tauri && cargo test            # Rust unit tests (policy, config, ShellStatus, pages, freeze guard, …)
cd desktop/src-tauri && cargo clippy --all-targets && cargo fmt --check   # lint + format gate (both clean)
node desktop/scripts/boot_check.mjs           # boot-page states
desktop/scripts/relaunch_drill.sh --ui http://127.0.0.1:8098   # restore/single-instance/autostart drill (scratch UI only;
                                              # back the scratch server with desktop/scripts/stub_backend.py)
```

Requirements: macOS 13+, Node ≥ 20 (npm), Rust (rustup; 1.80+), Xcode command-line tools. The first build
compiles ~400 crates (~1–2 min on an M4 Pro); later builds are incremental. Output:
`desktop/src-tauri/target/release/bundle/macos/SuryaDhana.app` (~8 MB).

**Build identity and rollback** (completeness-04). Every build carries a build id
`<git sha7>[-dirty]-<source hash>-<UTC yyyymmddTHHMMZ>[-devtools][-<profile>]` (round 3: a `--features devtools`
build, which has Web Inspector on the IPC-granted origin, and a non-release profile say so, and `--install` refuses
them without `--force`): the dirty flag is set while `desktop/` or this script
has uncommitted changes (today: always, `desktop/` is untracked), and the 8-hex source hash covers the shell's own
sources (src/, boot/, Cargo.toml/lock, tauri.conf.json, capabilities), so two different binaries never share an
id even on the same commit. It is shown in About SuryaDhana, the menu-bar item (`SuryaDhana 1.0.0 · <id>`),
`shell_info.build_id`, the boot page, the first app-log line, the self-test report (`meta.build_id`) and
`SuryaDhana --version`. CFBundleVersion is the same UTC time (`yyyymmddHHMM`, monotonic). `--install` keeps the
copy it replaces as `~/Library/Application Support/ai.suryadhana.terminal/previous/SuryaDhana.app.previous`
(renamed so macOS does not register a second SuryaDhana) with its id in `previous/BUILD`; the installed id is in
`…/installed-build`. `--rollback` swaps the two (and again rolls forward). Install and rollback quit only the copy
at the install path (Apple Event, then SIGTERM = Quit; never kill -9).

The first time the installed app runs (not in `--self-test`, not a debug build, not with
`SURYADHANA_NO_AUTOSTART=1`) it enables **Launch at Login** once (`~/Library/LaunchAgents/SuryaDhana.plist`,
label `SuryaDhana`, args `--autostart`) and records that in `<config>/.autostart-initialized`, so switching it
off is permanent (deleting `state.json` no longer turns it back on). The menu item *SuryaDhana ▸ Launch at Login*
and the tray toggle switch it off/on afterwards. The plist (written by the app itself, not a plugin) has:

* `KeepAlive {SuccessfulExit: false}` + `ThrottleInterval 20`: launchd relaunches the app 20 s after a crash, but
  never after ⌘Q / Quit (exit 0). It applies to the instance launchd started (at login, or after a crash). If the
  app crashes 4 times in 10 min, the next login-job launch exits 0 instead of starting (crash-loop breaker,
  logged), which stops the respawns; a manual launch always runs. The check runs before Tauri is built (round 3,
  R-RUST-04), so a start that fails while the app is being built (log plugin, a full disk, a plugin error) is
  counted too, and a login-job start that cannot even write its run marker stands down at once (stderr + the app
  log say why). Panics are logged (`[panic] …`) and their stderr lands in
  `~/Library/Logs/ai.suryadhana.terminal/launchd-stderr.log`. Activity Monitor's *Force Quit* (SIGKILL) counts as a
  crash and the app comes back 20 s later; ⌘Q, *Quit* in the menu-bar item and SIGTERM are a normal quit.
* **A copy opened by hand is relaunched too** (round 3, SECREL-06 / R-RUST-05). After ⌘Q and a reopen from the
  Dock, Finder or Spotlight (or for the copy that was running when Launch at Login was turned on) the app is NOT
  launchd's process, so KeepAlive does not cover it. Such a copy starts a **crash guard** (`src/supervise.rs`): a
  detached `/bin/sh` (own process group, `/dev/null` stdio, no inherited descriptors: never the single-instance
  socket) that checks every 15 s whether the app is alive. When the app is gone and its `run.json` still names it
  (a crash or kill -9, not a clean exit), the guard runs `launchctl kickstart gui/<uid>/SuryaDhana` (or
  `bootstrap` when the job is not loaded): the app comes back within ~15–20 s as the login job's process, under
  KeepAlive and the crash-loop breaker from then on. After a clean quit, or when Launch at Login was turned off
  meanwhile, the guard ends and starts nothing. It costs one sleeping shell (`ps`: `suryadhana-crash-guard`) and
  only exists for a copy that the Launch-at-Login entry starts (same executable), never in `--self-test`, a
  debug build or with `SURYADHANA_NO_AUTOSTART=1`. The menu-bar item says which applies: *Relaunch after a crash:
  on (login item)* / *on (crash guard for this copy)* / *off (Launch at Login is off …)*. While the entry exists the
  app also calls `-[NSApplication disableRelaunchOnLogin]`, so macOS's "Reopen windows when logging back in" never
  starts a second, LaunchServices copy that races the login job.
* **Changes take effect now** (wave 2, completeness-03). launchd reads a plist only when it loads it, so after
  the entry is written (Launch at Login on, first run, an upgrade or repair at launch) the app runs
  `launchctl bootout gui/<uid>/SuryaDhana` (nothing to do when not loaded) and `launchctl bootstrap gui/<uid>
  ~/Library/LaunchAgents/SuryaDhana.plist`; after it is removed (off), `bootout`. The bootstrap's RunAtLoad
  start finds the app running and exits at once without taking focus. Exception: when THIS instance is the
  login job's own process (launchd sets `XPC_SERVICE_NAME=SuryaDhana`), booting the job out would quit the app,
  so the change is left for the next login and the menu item says "Launch at Login (off from the next login)" /
  "(updated: applies at the next login)". `scripts/build_desktop.sh --install --relaunch` starts the new copy
  THROUGH launchd (`SuryaDhana --login-item-sync --start`: rewrite the entry for this copy, bootout + bootstrap)
  when Launch at Login is on, so launchd's own relaunch is in force at once (a copy opened by hand has the crash
  guard above).
  Every `launchctl` call is bounded (5 s). A drill's temp HOME shares the owner's per-user launchd domain, so
  it never touches launchd (it may inject a recording `launchctl` inside its own HOME: `SURYADHANA_LAUNCHCTL`).
* `AssociatedBundleIdentifiers = ai.suryadhana.terminal` and `ProcessType = Interactive`: System Settings ›
  General › Login Items lists it as SuryaDhana with its icon. If you switch it off under *Allow in the
  Background*, the menu says "Launch at Login (off in System Settings…)" and opens that pane.
* On every launch the entry is kept current: an old-format plist (the plugin's, without KeepAlive) is upgraded;
  an entry pointing at an app that no longer exists is rewritten for the running copy; an entry pointing at a
  build-directory copy is taken over by the installed copy (`/Applications/…`), never the other way round.
  `scripts/build_desktop.sh --install` also points an existing entry at the installed copy.

## Run

* Normal: open `/Applications/SuryaDhana.app` (or let it start at login). The boot screen checks the services and
  opens the terminal as soon as ui-api answers `/health` **and** `GET /` serves the UI (200 `text/html`).
* At login (`--autostart`, or within `startup_grace_secs` of the Mac's boot) and for `startup_grace_secs` after
  Start Stack, or while a watchdog run holds its lock, the boot screen shows **Starting the stack** with per-service
  progress, never the red down state, and offers no Start/Stop (the watchdog's login start takes 1–4 min). The
  login / Start grace needs the watchdog LaunchAgent (installed or loaded): without it nothing would start the
  stack, so the down state with the install command shows instead. A watchdog run is timed by its own lock
  (`.pids/watchdog/lock`), not by the app's uptime, and counts only while the lock's owner (`lock/owner`:
  `<pid> <boot field>`, written by the watchdog) is from this boot and is still the watchdog script (alive, command
  line naming `stack_watchdog`: a reused pid does not count), or, without an owner file, while the lock does not
  predate the boot (round 3, SECREL-05: a lock left by a power cut no longer shows "starting" and hides Start for up
  to 20 min after the reboot; the same rule as the watchdog's own `lock_is_stale`). The boot field is whatever the
  watchdog's `boot_epoch()` prints: today the `usec` part of `kern.boottime` (its sed is greedy), after a fix the
  `sec` part; both are accepted (round 4b: round 3 compared with `sec` only, so a real run never counted). A unit
  test runs the watchdog's own `take_lock` / `lock_is_stale` from `scripts/stack_watchdog.sh` in a temp dir and
  checks that the app and the watchdog agree. A run marker left by an unclean shutdown from BEFORE the current
  boot (power cut, forced restart: `run.json` older than `kern.boottime`) is not a crash: the login start keeps its
  grace and it is not counted towards the crash loop.
* **Not responding** (PM, 25 Oct: the live ui-api hung 14:40–14:48 with its event loop blocked while the boot page
  said "the watchdog is starting the stack"). Every `/health` probe is classified: 200 = up; connection refused =
  down (not running / restarting); a **timeout on a port that still accepts a TCP connection** (confirmed with a plain
  connect) = hung. Two such timeouts in a row make the service NOT RESPONDING (one is a blip). For ui-api the boot page
  then shows **UI-API NOT RESPONDING** with how long and names `./start-local.sh restart ui-api`. When the watchdog
  agent is loaded it also says the watchdog restarts a hung ui-api once it has failed two checks in a row (about
  3.5–5.5 min after it hangs, diagnostics saved to `.logs/hangs/` first: the hang rule in `scripts/stack_watchdog.sh`;
  data-service / master-controller never inside the restart freeze windows, master-controller not during an ICICI
  login (at most 10 min), at most 3 hang restarts per service per hour); without
  the agent it says nothing restarts it automatically. It offers Logs / Retry but no Start (`start-local.sh start`
  skips a running process, so Start cannot help).
  This state wins over the login / Start / watchdog-run grace. Rows, the menu-bar item (`◌ ui-api :8010 — NOT
  RESPONDING (port held, no /health answer)`, Start Stack disabled when the only problem is a hung service) and the
  "down" notification ("ui-api is not responding" + the restart command) say the same. Open terminal windows are never
  moved: the UI's own banner covers them and they recover when it answers. `ShellStatus` is unchanged (`up:false`).
* **A crashed page reloads itself** (round 3, completeness-final-03). When a window's WebKit content process ends
  (a WebKit bug, a GPU-process reset, a kill under memory pressure), WebKit tells the shell
  (`on_web_content_process_terminate`; wry implements that delegate method, which switches WebKit's own reload
  off). The shell logs it (`[window] main: its WebKit content process ended …`), reloads the window at its current
  page (or shows the boot page until the terminal is reachable) and sends one notice ("SuryaDhana reloaded a
  window", at most one per 10 min). At most 3 automatic reloads per window in 5 min: the 4th crash keeps the window
  on the boot page as **PAGE STOPPED** (how often, what to check) with *Open terminal now*; ⌘R works too. A page
  that crashes on load can therefore never loop. WebKit resets a crashed view's URL to nil, so the window is
  reloaded at the page the 8 s status broadcast last saw (in-page tab changes included), not at an older target.
  **Never call tauri's `WebviewWindow::url()` in the shell**: wry 0.57.1 unwraps that nil URL and the panic on the
  main thread ends the whole app (found by the round-3 self-test); every URL read goes through
  `windows::webview_url` / `webview_url_of`, which reads `WKWebView.URL` itself and treats nil as "no URL".
* **The stack's notifications are native** (round 3, K5). Every 15 s while the terminal is reachable and its port
  listener is trusted, the shell reads `GET /api/notifications/feed?since=<epoch ms>` (ui-api; price alerts,
  filings, results, moves, closing / pre-market notes) and shows new events as SuryaDhana banners whatever page is
  open, also with every window closed to the menu bar. It follows the feed's contract: `since` is the server's
  `next_since` (newest event minus a 60 s overlap), events are de-duplicated by their stable id, and `banner: false`
  records (wrap, journal) stay in the in-page inbox only. A first start (no `notify-feed.json`) announces nothing
  old; the cursor survives restarts, and events missed while the app was closed are shown only when at most 30 min
  old. Throttled like `shell_notify` (the same 20-a-minute limiter, shared with the pages' banners), at most 3
  banners per poll (the newest; older ones in one "N more SuryaDhana alerts" banner), titles and bodies validated
  the same way. A failing feed (an older ui-api without the endpoint) backs off to 60 s and is logged once. While it
  works the shell touches `notify-sink.alive` (config dir, once a minute) so the scheduler can skip its own
  osascript banner (master_controller `_app_is_notification_sink`; osascript stays its fallback when the app is not
  running). Round 4b: only while macOS ALLOWS SuryaDhana's notifications and not for a poll whose banners were all
  throttled; the file is removed when notifications are off and on a clean quit, so the scheduler's own banner is
  back at once.
* **Notifications off** (round 4b). macOS's permission is read every 60 s. While it is *denied* the menu-bar item
  shows one extra line, *Notifications are off — System Settings › Notifications › SuryaDhana*, and the boot page's
  footer says the same. Nothing pops up and nothing nags; a click on that menu line (and only that) opens System
  Settings › Notifications at SuryaDhana. The app log notes the change once.
* **ICICI line** (round 4b, P4). The menu-bar item and the boot page read ui-api's `error_kind` on
  `/api/positions/connection-status`: `network` → *ICICI — unreachable (network)* (amber on the boot page, not a
  login problem: no "send /login", no "session expired" notification); `credentials` → API key/secret missing or
  rejected (fix on BRKR); `expired` → *expired: send /login in Telegram* as before; a missing field (older ui-api),
  `unknown` or null → as before (not connected = expired). `ShellStatus.icici` stays `connected|expired|unknown`
  (an outage and missing credentials are `unknown` there).
* Closing the main window hides it (leaving full screen first, so no empty black Space stays behind); the app keeps
  running in the menu bar (notifications continue). A Dock click brings back the last-used window (unminimizing
  it), tray *Open Terminal* the main window. ⌘Q (or SIGTERM, e.g. at logout) quits and saves the window set.
* ⌘N opens another terminal window (max 8 windows; at the limit the Mac beeps) cascaded from the focused window,
  on its display. Window geometry (per label), page zoom and the set of open windows with their pages are
  restored on the next launch. Automatic window tabbing is off (the custom title strip assumes no tab bar).
* App menu *Settings…* (⌘,) explains the settings file in a native dialog and opens `config.json` in TextEdit
  ("Edit config.json…"; changes apply at the next launch). Launch at Login and page zoom live in the menus. (Round 1's
  ⌘, opened the SYS telemetry page, which has no settings: removed.) *File ▸ Show Latest Download* (⌥⌘L, also in the
  menu-bar item) reveals the latest saved file in Finder.
* *File ▸ Open Current Page in New Window* (⌥⌘N) opens the focused window's exact page (tab, `?sym=` stock, filters);
  ⌘N opens the same tab. *File ▸ Print…* (⌘P, round 4b R9) opens WebKit's print panel (printer or Save as PDF) as a
  sheet on the focused window; the boot page, a window still loading, a hidden or minimized window and a second ⌘P
  while the panel is up get a beep instead. ⌘F is deliberately not a menu key: the page's find bar gets it (⌃⌘F is
  Enter Full Screen). *Go ▸ Back* (⌘[) / *Forward* (⌘]) walk the focused window's page history (never past its
  first terminal page: the boot page before it is refused by the navigation policy). *Help ▸ Keyboard Shortcuts*
  lists the ⌘ keys. *View ▸ Zoom In / Out / Actual Size* (⌘= ⌘- ⌘0, 50–200 %) is per window, saved with the
  session, and a new window takes the zoom of the window it was opened from.
* `--self-test <out.json>` (or env `SURYADHANA_SELFTEST_OUT`): see *Self-test* below.

## Configuration

`~/Library/Application Support/ai.suryadhana.terminal/config.json` (created with defaults; missing keys are
filled in; an unparseable file is left untouched and defaults are used):

```json
{
  "repo_root": "/Users/sudheer/MahaKubera_108/SuryaDhana_AI",
  "ui_url": "http://127.0.0.1:8010",
  "data_service_url": "http://127.0.0.1:8001",
  "controller_url": "http://127.0.0.1:8008",
  "nifty_in_menubar": true,
  "notify_service_changes": true,
  "devtools": false,
  "frame_hosts": ["tradingview.com", "tradingview-widget.com"],
  "startup_grace_secs": 180,
  "trusted_python_prefixes": [],
  "verify_ui_listener": true
}
```

* Every URL must be plain `http` on `127.0.0.1` or `localhost` (anything else is rejected and logged).
* `SURYADHANA_UI_URL` overrides `ui_url` and `SURYADHANA_STARTUP_GRACE_S` overrides `startup_grace_secs` for
  testing (same validation; not persisted).
* `devtools: true` adds *View ▸ Developer Tools* (⌥⌘I) and the inspector context menu **only in a build made with
  `cargo build --features devtools`**; release builds (`scripts/build_desktop.sh`) never contain Web Inspector.
* `frame_hosts`: hosts that may load as **embedded frames** inside terminal pages (the TradingView chart
  widget), **https only**. A top-level navigation to them is still bounced to the default browser.
* `startup_grace_secs` (0–900): how long the boot screen shows "Starting the stack" after a login start / Start.
* `trusted_python_prefixes`: extra absolute executable-path prefixes the port-squatting guard accepts (e.g. a pyenv
  install, or a venv made with `--copies`); compared as strings, never stat'ed. Default `[]`: Homebrew and python.org
  CPython only. `verify_ui_listener: false` turns the guard off (only for a non-Python dev server). The round-1 key
  `stack_python` is ignored (logged when set): the guard no longer resolves the interpreter, which lives under ~/Desktop.
* Session state: `state.json` (open windows + URLs + zoom) and `.window-state.json` (geometry) next to
  `config.json`; `.autostart-initialized` (first-run marker), `run.json` / `crashes.json` (crash bookkeeping),
  `notify-feed.json` (the K5 feed cursor: delete it to restart following from the newest event) and
  `notify-sink.alive` (the sink heartbeat).

## Shell ↔ UI contract v1 (PLAN.md §5)

* Detection: every window gets, at document start,
  `window.__SURYADHANA_SHELL__ = Object.freeze({api: 1, version, build, platform: 'macos', features})` (read-only
  property). `features` (round 3, additive) names what this shell does beyond v1: `notification_feed` = the shell
  posts the stack's notification feed (price alerts etc.) as native banners itself, so a page must not post the
  same events again (WTCH's alert check; an older app without the name keeps the page's own banner).
* Commands granted to the terminal origin (`invoke` via `window.__TAURI_INTERNALS__.invoke`): `shell_info`,
  `shell_status`, `shell_notify`, `shell_notification_permission`, `shell_request_notification_permission`,
  `shell_save_download`, `shell_open_external`, `shell_new_window`, `shell_set_title`. All arguments are
  validated in Rust (`src/policy.rs`).
* Wave-2 additions (additive): `shell_info.build_id`; `shell_new_window {tab?, sym?}` (contract K4: `sym` must match
  `^[A-Z0-9&_.-]{1,20}$`, validated in Rust; the window opens `ui_url/?tab=<tab>&sym=<SYM>`, `&` URL-encoded) — the
  native ⌥⌘N and `window.open` of a same-origin `?sym=` URL use the same path; the page zoom (contract K3) as
  `window.__SURYADHANA_ZOOM__` (set at document start, at every terminal commit) and the event
  `{type:'zoom', factor}` after every change and every terminal page load, so the title strip can keep its
  traffic-light inset at a constant screen width (84 px / factor). `shell_request_notification_permission` opens
  System Settings at most once a minute and serializes requests (one waits on the macOS prompt at a time).
* Boot-only: `boot_status {refresh?}`, `stack_start`, `stack_stop`, `open_logs {target?: 'stack'|'app'}`,
  `open_terminal {tab?}`.
* Events: `window.dispatchEvent(new CustomEvent('suryadhana:shell', {detail}))` with `{type:'status', status}`,
  `{type:'goto', tab}` (Go menu, tray, ⌘1–⌘9), `{type:'command-bar'}` (Go ▸ GO Bar…), `{type:'build-changed', build}`
  (served build ≠ the build the window loaded).
* **Status cadence** (contract note): a changed status goes out at most every 5 s, and a heartbeat at least
  every **8 s** even when nothing changed (a 1 s ticker checks it, so the largest gap is ≤ 9 s; the self-test
  measures it as `status_heartbeat`). The UI's side of this contract is `ui/components/desktop/status.ts`:
  `SHELL_STATUS_MAX_INTERVAL_MS = 10_000` (the shell pushes at least this often), dots grey after
  `STATUS_STALE_MS` (3 × that + 5 s) judged by the status' own `at` (the time of the shell's last 5 s poll, at
  most ~13 s old while a stalled ui-api makes polls slow), and a `shell_status` pull after 10 s without a push.
* `ShellStatus.nifty` is `null` while the quote is **stale** (two failed fetches in a row, or a quote whose NSE
  time is > 5 min old during 09:15–15:30 IST); outside NSE hours it carries the last close (the tray adds
  "· closed"). Fresh data beats the calendar (round 4b, R10): an NSE print stamped within 3 min of now is live
  whatever the day (Muhurat, Sun 8 Nov 2026; a special Saturday), the same window as the UI header
  (`NSE_PRINT_MAX_AGE_MS`); a side effect is that a normal day's 15:30 print reads live until 15:33. `ui_api.up` uses a 5 s `/health` timeout (the watchdog tolerates 8 s).
* `shell_notification_permission` / `shell_request_notification_permission` report the real macOS authorization
  (UNUserNotificationCenter): `granted` / `denied` / `default` (not decided yet, or unknown). The request shows the
  system prompt once. `shell_save_download` returns `{path: "~/Downloads/<name>"}` (display form, no account name).
* The overlay title bar leaves the traffic lights at (14, 18) pt (screen points: they do not scale with page zoom, hence the zoom event); the UI's title strip should carry
  `data-tauri-drag-region` (or `="deep"`) to be draggable — the remote capability grants
  `core:window:allow-start-dragging` (+ `allow-internal-toggle-maximize` for double-click zoom) for exactly that.

## Security model

* **Least-privilege IPC.** App commands are declared in `build.rs` (`AppManifest`), so Tauri enforces the ACL on
  every app command. The boot page (local `tauri://localhost`) gets the 5 boot commands; exactly the configured
  terminal origin (default `http://127.0.0.1:8010`, no `localhost` alias) gets the 9 `shell_*` commands plus
  window dragging (`core:window:allow-start-dragging` for the overlay title strip's `data-tauri-drag-region`,
  `allow-internal-toggle-maximize` for double-click zoom; a contract-v1 amendment the PM approves). No core
  event/webview/fs/shell/opener/notification/autostart/log plugin permission is granted to remote content, so a
  page on :8010 cannot call plugin commands, listen to app events, or invoke `stack_*`. Each command also
  re-checks that its caller is exactly the terminal origin (defence in depth).
* **Navigation allowlist** (`policy::navigation_decision`): the boot origin (only when the shell itself initiated
  the navigation: the remote page cannot send a window back to the privileged boot page), the configured ui
  origin (its alias spelling, `localhost` ↔ `127.0.0.1` on the same port, is cancelled and re-loaded on the
  configured spelling, so every terminal window sits on the one origin that has the IPC grant and one
  localStorage), `about:blank`/`srcdoc`, same-origin `blob:`, and embedded `frame_hosts`. External http(s) → cancelled and opened in the default browser. Other loopback ports, `file:`,
  `javascript:`, `data:`, custom schemes → denied and logged. A main-frame load that still lands off the
  allowlist is bounced back. `window.open`/`target=_blank`: same origin → a new terminal window, external →
  default browser.
* **Downloads**: `shell_save_download` (base64 ≤ 50 MB) and WebKit downloads (`<a download>`, blob) write only
  into `~/Downloads`; only the terminal origin and its own `blob:` URLs may download (never `data:`, which any
  frame can mint). Names: basename sanitized to `[A-Za-z0-9._ -]` (≤ 120 chars), then an **extension allowlist**
  (`csv tsv txt json md pdf png jpg jpeg xlsx`: what the terminal exports and RSCH serves); anything else gets
  `.txt` appended (`Q3.zip` → `Q3.zip.txt`). Unique ` (n)` suffix checked with `symlink_metadata` (a dangling
  symlink counts as taken), `O_EXCL` create. Every file is tagged **`com.apple.quarantine`** (`0083;<time>;SuryaDhana;`,
  set on the open file descriptor, or on the path without following symlinks once WebKit finishes), so Gatekeeper
  assesses whatever it is on first open. Chosen over `LSFileQuarantineEnabled`, which would quarantine every file
  the app and its children create (config, logs, and the stack started from the app). Limits for all windows
  together: 10 downloads/min, 200 MB/hour, nothing written with < 5 GB free. WebKit downloads (size known only when
  they finish) are charged to the SAME hourly budget at Finished: one that takes the hour over 200 MB, or the volume
  under 5 GB free, is removed again ("Could not save … removed"), and while the hour is used up no new download of
  either kind starts. Feedback: "Saved to Downloads" or "Could not save …" (EPERM → the Files and Folders setting to
  change). External browser opens: 20/min.
* **Boot page CSP**: `default-src 'none'; script-src 'self'; style-src 'self'; connect-src ipc: http://ipc.localhost; …`
  (self-test proves an injected inline script does not run).
* **Secrets**: the ICICI connection-status body is deserialized into two booleans and `error_kind` and dropped; it is never logged
  (it holds a `login_url` with the API key). Logged URLs are redacted to scheme+host+path (no query strings).
* **Port squatting** (reworked in wave 2). While ui-api is down (a crash, or the up-to-2-min watchdog restart),
  any local process, including a same-user *sandboxed* app with the network-server entitlement, could bind
  :8010. A window on that origin would then render whatever it serves inside a trusted SuryaDhana window (a
  pixel-perfect fake ICICI credential form, fake notifications) and hold the 9 remote commands: notifications,
  browser opens, files into ~/Downloads, up to 8 windows. It would also keep :8010, so the watchdog could not
  restart ui-api.
  **Guard** (`src/trust.rs`, `policy::listener_trust`), from kernel facts only: the listeners on the ui port are
  found in-process with libproc (`proc_listallpids` → `PROC_PIDLISTFDS` → `PROC_PIDFDSOCKETINFO`, TCP LISTEN on
  that port, IPv4 or IPv6), each one's owner and executable from `proc_pidinfo` / `proc_pidpath`. Trusted = every
  listener is this user's AND its executable is a CPython in a Homebrew keg
  (`/opt/homebrew|/usr/local` `/Cellar/python@3.N/<any 3.N.x>/Frameworks/Python.framework/Versions/3.N/…Python.app/
  Contents/MacOS/Python` or `…/bin/python3[.N]`) or the python.org framework (`/Library/Frameworks/Python.framework/
  Versions/3.N/…`), or under a `trusted_python_prefixes` entry. It is a pure string rule: nothing on disk is read,
  stat'ed or canonicalized, so the app never touches ~/Desktop (macOS privacy would prompt for, or silently deny,
  the app's own access: round 1 canonicalized the venv python there, with no timeout), and ANY patch version of
  the keg matches, so the ui-api that keeps running after `brew upgrade python@3.13` (old keg path, possibly
  already deleted) is still trusted. A non-root process cannot see another account's sockets: when no listener is
  visible the guard connects once and lists again; the port answering with nobody of this account holding it is
  another account's (or root's) process. The whole probe runs on the blocking pool under a hard 5 s timeout.
  Verdicts: **Foreign** (definitive: another program, another user, or an invisible holder) keeps every window
  on the boot page, which names the pid and executable, and pulls open terminal windows back to it;
  **Unknown** (the probe failed or timed out, or the listener vanished mid-check: a ui-api restart race) never
  evicts and never holds a window back; it is retried within 5 s and the menu-bar item says "port not verified
  (retrying)". **Round 3** (R-RUST-01/02, SECREL-04): there is no cached pass any more; the guard runs on EVERY
  fast poll that finds the port held (every 5 s, every 1 s while a window waits; about 2 ms of CPU), also while
  `/health` fails or hangs, so a listener swapped in between two polls is refused at the next poll and open
  windows trust the port for at most one poll (round 2: up to 30 s). A pass pins the listeners (pid + kernel start
  time); when a live listener's executable can no longer be read (deleted after it started: `brew cleanup` after
  `brew upgrade`, or a binary that unlinked itself), it stays trusted only if it is exactly a pinned process (the
  running ui-api), otherwise it is **Unverifiable**: treated like Foreign (new windows held, open ones pulled back),
  the boot page says **TERMINAL PORT NOT VERIFIED** and names `./start-local.sh restart ui-api`. A pid that is
  reused never inherits a pin.
  **Residual risk, stated plainly**: a same-user process that runs a Homebrew or python.org CPython passes. That
  includes a *sandboxed* app (network-server entitlement) that execs `/opt/homebrew/bin/python3` as a child: the
  child inherits the sandbox (it cannot read the repo or `.env`) but it does run the trusted interpreter and can
  serve :8010 while ui-api is down. Homebrew's prefix is owned by this user (not root), so any NON-sandboxed process
  of this user could also place a fake keg there, but such a process already has the whole account. Closing the
  sandboxed-child gap needs a shared secret between ui-api and the shell (a ui-api change, not in the shell's
  files). Downloads are quarantined and extension-limited whatever the verdict.
* **Single instance**: the lock is a Unix socket in /tmp (the plugin's path, so builds hand off across an
  upgrade). Round 3 (SECREL-10): a socket file there that belongs to another account, or a symlink, is never
  connected to (another user could otherwise make every launch hand off and exit, and the sticky bit stops this
  user from removing it); the app then runs without the lock and logs why. WebKit downloads: one per URL at a time
  (a second request while one is still downloading is refused with "already being saved"), so each file is
  quarantined and charged to the byte budget (R-RUST-03).
* **Stack control** never runs the stack's Python: Start clears the paused markers and runs `launchctl kickstart`
  of the watchdog LaunchAgent **without `-k`** (a watchdog run that is already starting the stack is left alone);
  when the agent is not loaded its installed plist is loaded with `launchctl bootstrap`; when it is not installed,
  Start refuses and names `scripts/install_launch_agents.sh install` (it never spawns `start-local.sh` under the
  app's own privacy grant). Stop is behind a native confirm and refused in the IST freeze windows
  07:45–09:20 / 18:30–21:15 (computed in Asia/Kolkata regardless of the Mac's timezone).

## Logs

`~/Library/Logs/ai.suryadhana.terminal/suryadhana.log` (5 MB × 5 rotation): startup, config warnings, health
transitions, blocked navigations, downloads, IPC validation failures, stack actions, panics, the port-squatting
guard. `--self-test` never writes there (its log stays in its temp dir and is copied to `<out>.app.log`).
Stop Stack appends to `<repo>/.logs/desktop-stack.log`. Help ▸ Open App Logs Folder / Open Stack Logs Folder.

Notifications: a service is announced down only after it stayed down 20 s (restarts never notify), services that
went down together share one notification, "back up" follows only an announced outage (separate from the down
throttle), services stopped on purpose (`.pids/paused/<svc>`) are never announced, and nothing is announced for
the stack coming up after login. The same service's next outage within 10 min is silent (crash loops). The stack's
own events (price alerts etc.) come from the K5 feed (see *Run*); `[feed]` log lines say when it is followed,
unavailable, or how many events were shown / too old.

## Self-test

`SuryaDhana.app/Contents/MacOS/SuryaDhana --self-test out.json` runs the real app in isolation (temp
state/window-state/Downloads/app log, incognito webviews, no single-instance lock, autostart read-only,
notifications and browser opens recorded, stack commands refused) and writes `{passed, checks:[{name, ok,
detail, ms}], meta}`, exiting 0/1 within 60 s; the app log is copied to `out.json.app.log`. It is safe while the
installed app runs. Checks: boot paint < 500 ms (+ a paint-independent boot DOM-ready time), boot CSP, terminal
loaded/interactive, the port-squatting guard passed (a definitive Trusted verdict), the detection object, IPC round trip from the remote page,
`ShellStatus` shape, boot/stack/plugin/event commands rejected from the remote page, argument validation,
external-open routing, `shell_save_download` (+ quarantine xattr), the extension allowlist (`.zip`/`.command` →
`.txt`), download feedback, the WebKit download path (+ quarantine) and its `data:` refusal, the UI-bridge download
path, every saved file quarantined, event delivery and the UI's `goto` handling, the zoom event + variable
(contract K3), `shell_new_window` with a `sym` deep link (`M&M` → `sym=M%26M`, K4) open + close, `shell_info.build_id`,
session persistence, the status heartbeat (largest gap ≤ 10 s), a crashed page recovering by itself (round 3:
the main window's WebContent process is SIGKILLed, the window must be back on the terminal in a new content process
with the notice), navigation guard, alias-origin canonicalization, Back (⌘[) never leaving the terminal, the K5
feed (against `stub_backend.py`: nothing old on the first start, the fresh event exactly once, the 2-hour-old one
never, the cursor in the temp dir),
Go menu with 42 pages + ⌘1–⌘9, Edit clipboard items, tray, autostart state unchanged, the real notification
authorization, shell RSS and total RSS (budget 500 MB), isolation (incl. the log). Round 4b adds: Print… refused on
the boot page; on the terminal the print panel appears as a sheet, a second Print… is refused, Cancel closes it and
no job file is written (the shared print info is first pointed at a temp PDF, so nothing can reach a printer); the
real menu bar's key equivalents (⌘P = Print…, no plain ⌘F); the tray's ICICI line for the reported `error_kind`
(the stub reports an outage: *unreachable (network)*); a fresh NIFTY print shows live in the tray whatever the
calendar (the stub's print is stamped now); the notification hint matches macOS's answer and System Settings was
never opened by itself.
When the terminal never loads the run fails by design and checks the boot page instead: the down state with its
actions (closed port), "not responding" (a listener that never answers, also with `--autostart`: it must win over the grace), the start-up grace (closed port + `--autostart`, `SURYADHANA_STARTUP_GRACE_S`), the "no UI
release" remedy (a server answering 503 + `/ready` `ui: missing`), the port-squatting refusal (a server run by
another interpreter), or the unverifiable listener (round 3: a server whose executable was deleted after it bound
the port).

A check that cannot be measured in the current environment is reported as `"ok": true, "skipped": true` and
listed in `meta.skipped` (the summary prints `SKIP`). Today that is only `boot_page_painted` while the macOS
screen is locked: WebKit renders no frames for a locked session, so the < 500 ms paint budget can only be
measured on an unlocked screen (`meta.screen_locked` says which case a report is).

## Idle measurement (AC-13, C-PERF-03)

The self-test's resource numbers are taken right after its own checks, in the first minute after launch (often with
the screen locked): they measure start-up, not idle. The idle budget (< 3 % CPU, < 500 MB for one window) is
measured on the RUNNING app instead, without launching anything:

```bash
/Users/sudheer/Desktop/jupyter_env/bin/python desktop/scripts/measure_idle.py --seconds 600 \
    --json reports/desktop_app/perf/idle_$(date +%Y%m%d-%H%M).json
```

Run it **with the screen unlocked and a terminal window visible** (not hidden to the menu bar), at least 5 min after
the app started and after any ui-api restart or UI release swap; then again with 3 windows (⌘N), on BRF and on
EQS. It prints, per process (the shell and the WebKit WebContent / Networking / GPU helpers macOS attributes to it)
and in total, CPU %, wakeups/s and memory (phys_footprint, Activity Monitor's "Memory"), plus the shell's busiest
threads by name (CVDisplayLink, JavaScriptCore scavenger, main, tokio workers), so a regression can be attributed.
It warns (and marks the sample invalid in the JSON) when the screen is locked, no window is visible, the app or
ui-api started less than 5 min ago, or the window is shorter than 2 min.

## Troubleshooting

| Symptom | Check |
|---|---|
| Boot screen says "Starting the stack" | normal for 1–4 min after login / Start; `.logs/watchdog.log` shows progress |
| Boot screen stays on "Waiting for ui-api" / "STACK DOWN" | `./start-local.sh status`; boot screen *Start stack* (after 15 s down) or tray ▸ Start Stack |
| "NO TERMINAL UI RELEASE" (GET / = HTTP 503, `/ready` `ui: missing`) | `./start-local.sh build-ui` (≈ 15 s), or `./start-local.sh build-ui --rollback` |
| "UI-API NOT RESPONDING" | ui-api holds :8010 but `/health` times out (event loop blocked). The watchdog restarts it after two failed checks (about 3.5–5.5 min after it hangs; diagnostics in `.logs/hangs/`); to restart it now: `./start-local.sh restart ui-api`, then `.logs/ui-api.log` for what blocked it |
| "TERMINAL PORT NOT TRUSTED" | another program holds :8010 (pid + path on the screen): quit it, `./start-local.sh restart ui-api`; a non-Homebrew interpreter of your own: add its prefix to `trusted_python_prefixes` |
| Menu bar says "port not verified (retrying)" | the port check was inconclusive (ui-api restarting); windows stay open; it clears within seconds, else see `[trust]` in the app log |
| "TERMINAL PORT NOT VERIFIED" | a process of yours holds :8010 but its executable no longer exists and it was never verified (typically: Python upgraded by `brew upgrade` while the app was closed, or something that deleted its own binary): `./start-local.sh restart ui-api` |
| "PAGE STOPPED" in a window | its WebKit content process ended 4 times in 5 min; *Open terminal now* or ⌘R; check memory pressure (Activity Monitor) and `[window] … content process ended` in the app log |
| A price alert shows twice (SuryaDhana + Script Editor) | until master_controller skips osascript while `notify-sink.alive` is fresh, the scheduler's own banner still appears; turning off Script Editor's notifications in System Settings hides it |
| Menu bar says "Notifications are off …" | macOS has SuryaDhana's notifications off: click that line (System Settings › Notifications › SuryaDhana) and allow them; meanwhile the scheduler's own banner (Script Editor) stays on |
| Menu bar says "ICICI — unreachable (network)" | ICICI's API did not answer ui-api (after its retries): not a login problem, nothing to send; it clears by itself. If it lasts, check the network / ICICI status |
| A new shell build misbehaves | `scripts/build_desktop.sh --rollback --relaunch` (the previous copy is kept by every `--install`) |
| "macOS IS BLOCKING THE STACK" | System Settings › Privacy & Security › Files and Folders → allow Python the Desktop folder |
| Menu bar says "NIFTY — stale" | data-service is not answering (or the quote froze during NSE hours): `./start-local.sh status` |
| Export says "Could not save … Files and Folders" | allow SuryaDhana the Downloads folder in System Settings › Privacy & Security |
| Terminal loads but ⌘C/⌘V do nothing | the Edit menu must exist (it does); check a custom key handler in the page |
| External link does nothing | `suryadhana.log` → `[nav]` lines (blocked vs opened) |
| App does not start at login | menu ▸ Launch at Login ✓ (or "off in System Settings…"); System Settings › General › Login Items › Allow in the Background; `launchctl print gui/$(id -u)/SuryaDhana`; `~/Library/LaunchAgents/SuryaDhana.plist` |
| App did not come back after a crash | the menu-bar item says *Relaunch after a crash: …*: off when Launch at Login is off (or blocked in System Settings); 4 crashes in 10 min stop the relaunch: `grep -nE 'panic|crash guard|crash relaunch' ~/Library/Logs/ai.suryadhana.terminal/suryadhana.log` |
| "SuryaDhana is damaged / unidentified developer" | ad-hoc signed build: right-click ▸ Open once, or `xattr -dr com.apple.quarantine /Applications/SuryaDhana.app` |
| Reset window layout | quit, delete `.window-state.json` and `state.json` in the config dir (Launch at Login stays as you set it) |
